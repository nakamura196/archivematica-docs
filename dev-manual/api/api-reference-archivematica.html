Archivematica API¶

Archivematica APIが提供：

  • 基本的なワークフロー機能をカバー。

  • Storage Serviceへのプロキシサポート。

  • ユニットのステータスまたは処理設定の詳細への公開。

リソースとエンドポイント¶

Archivematica APIのエンドポイントは、以下のリソースカテゴリに分類されます：

  • 転送

  • インジェスト

  • 管理

  • ユニット

  • その他

  • ベータ

転送¶

転送とは、デジタルオブジェクトをArchivematicaに移動し、SIP（Submission Information Package）に変換するプロセスを指します。Transferタブでは、コンテンツをArchivematicaで保存するための準備を行います。

転送開始¶

POST

/api/transfer/start_transfer/

Archive maticaで転送を開始します。

リクエストボディのパラメーター：

Tip

以下の表のパラメーターは、リクエストボディにキーと値のペアを持つJSONオブジェクトとして送信できます。

name

転送の名前

type

新しい転送のタイプ。有効な値は、standard、zipfile、unzip bag、zip bag、dspace、maildir、TRIM、dataverseです。デフォルトでは、standardです。

accession

新規転送のAccession番号。

paths[]

新しい転送にコピーされるbase64エンコードされた <location_uuid>:<relative_path> のリスト。場所のUUIDは、このパイプラインに関連付けられている必要があり、相対パスは、場所からの相対パスでなければなりません。

row_ids[]

ディスクイメージインジェストに関連するTransferMetadataSetのID。 [""] として指定できます．

リクエスト例：

curl --request POST \
  http://my_archivematica_instance.archivematica.org/api/transfer/
  start_transfer/ \
  -H 'Authorization: ApiKey [_your_username_]:[_your_ApiKey_]' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'name=mc_api_transfer&type=standard&accession=2019-1234&paths%5B%5D='\
  ''M2JlYzc0MmYtMjBjMy00ZjBlLThjMzEtZGFmYTVlYzE4ZmRmOmNlbnRvcy9hcmNoaXZlbWF0aWNh
  LXNhbXBsZWRhdGEvU2FtcGxlVHJhbnNmZXJzL0RlbW9UcmFuc2ZlckNTVg%3D%3D'\''&rows_
  id%5B%5D='

レスポンス例：

HTTP/1.1 200
status: 200
Server: nginx/1.12.2
Date: Thu, 15 Aug 2019 06:37:41 GMT
Content-Type: application/json
Transfer-Encoding: chunked
Connection: keep-alive
Vary: Accept-Language, Cookie
Content-Language: en

{
    "path": "/var/archivematica/sharedDirectory/watchedDirectories/
    activeTransfers/standardTransfer/mc_api_transfer_1/",
    "message": "Copy successful."
}

転送を承認¶

POST

/api/transfer/approve/

開始を待っている転送を承認します。

リクエストボディのパラメーター：

type

転送のタイプ。有効な値は、standard、zipfile、unzip bag、zip bag、dspace、maildir、TRIM、dataverseです。デフォルトではstandardです。

directory

転送が現在存在するディレクトリ。

リクエスト例：

curl -X POST \
  http://my_archivematica_instance.archivematica.org/api/transfer/approve/ \
  -H 'Authorization: ApiKey [_your_username_]:[_your_ApiKey_]' \
    -H 'Content-Type: application/x-www-form-urlencoded' \
  -H 'Host: my_archivematica_instance.archivematica.org' \
   -d 'directory=mc-api-test-2&type=standard&rows_id%5B%5D='

レスポンスの定義：

message

"承認に成功。"

uuid

承認された転送のUUID

レスポンス例：

{
    "message": "Approval successful.",
    "uuid": "a8791a46-ac73-4c7d-8c60-0673524226e3"
}

ステータス¶

GET

/api/transfer/status/<transfer UUID>/

転送のステータスを返す。

レスポンスの定義：

status

FAILED、REJECTED、USER_INPUT、COMPLETE、PROCESSINGのいずれか1つ

文字列

name

転送の名前（例："imgs"）

文字列

sip_uuid

ステータスが、COMPLETEの場合、このフィールドは、SIPのUUIDまたは「BACKLOG」のいずれかで存在します

文字列

microservice

現在のマイクロサービスの名前

文字列

directory

ディレクトリ名、例："imgs-52dd0c01-e803-423a-be5f-b592b5d5d61c"

文字列

path

転送へのフルパス、例："/var/archivematica/sharedD/var/archivematica/sharedDirectory/watchedDirectories/SIPCreation/ completedTransfers/imgs-52dd0c01-e803-423a-be5f-b592b5d5d61c"

文字列

message

"<transfer UUID>からステータスの取得に成功。"

文字列

type

"転送"

文字列

uuid

転送の UUID（例："52dd0c01-e803-423a-be5f-b592b5d5d61c"）

文字列

注釈

このエンドポイントのコンシューマーは、Archivematicaがsip_uuidなしでCOMPLETEステータスを返す可能性があります。そのため、インジェスト後に作成されるAIPのUUIDを使用したいコンシューマーは、COMPLETEというステータスと、BACKLOGと等しくないsip_uuidの存在をテストし、確実に取得する必要があります。これは、このデータが利用可能になる間に、ステータスエンドポイントへの追加の呼び出しを意味するかもしれません。

リクエスト例：

curl -X GET \
  http://my_archivematica_instance.archivematica.org/api/transfer/
  status/89fd478d-c896-461a-baec-5d1faf661020/ \
  -H 'Authorization: ApiKey [_your_username_]:[_your_ApiKey_]' \
  -H 'Host: my_archivematica_instance.archivematica.org'

レスポンス例：

{
    "status": "COMPLETE",
    "name": "ab",
    "microservice": "Check transfer directory for objects",
    "directory": "ab-89fd478d-c896-461a-baec-5d1faf661020",
    "path": "/var/archivematica/sharedDirectory/watchedDirectories/SIPCreation/
    completedTransfers/ab-89fd478d-c896-461a-baec-5d1faf661020/",
    "message": "Fetched status for 89fd478d-c896-461a-baec-5d1faf661020
    successfully.",
    "type": "transfer",
    "uuid": "89fd478d-c896-461a-baec-5d1faf661020"
}

再インジェストの開始¶

注釈

Start reインジェストエンドポイントは、Storage Service側の AIPの再インジェスト エンドポイントを補完します。再インジェストが開始されると、Archivematicaは、ストレージからAIPをフェッチし、抽出し、その完全性を確認するためにfixityを実行します。その後、Archivematicaは再インジェストの種類に応じて環境をセットアップし、Storage Service側のエンドポイントがArchivematica Start reインジェストエンドポイントを呼び出します。

POST

/api/transfer/reingest

フル再イインジェストを開始します。

リクエストボディのパラメーター：

name

AIPの名前。AIPは、 %sharedDirectory%/tmp/<name> にもあるはずです。

uuid

再インジェストするAIPのUUID。

レスポンスの定義：

message

"承認に成功。"

reingest_uuid

再インジェストした転送のUUID。

インジェスト¶

インジェストとは、デジタルオブジェクトがSIPにパッケージ化され、正規化、AIPへのパッケージ化、DIPの生成を可能にするマイクロサービスを通じて実行されるプロセスを指します。

ステータス¶

GET

/ingest/status/<unit_UUID>/

SIP のステータスを返します。

レスポンスの定義：

status

FAILED、REJECTED、USER_INPUT、COMPLETE、PROCESSINGのいずれか1つ。

name

SIPの名前（例："imgs"）。

microservices

現在のマイクロサービスの名前

directory

ディレクトリ名（例："imgs-52dd0c01-e803-423a-be5f-b592b5d5d61c"）

path

転送へのフルパス（例："/var/archivematica/sharedDirectory/ currentlyProcessing/imgs-52dd0c01-e803-423a-be5f/b592b5d5d61c/"）。

message

"<SIP UUID>のステータス取得に成功。"

type

"SIP"

uuid

SIPのUUID、例えば"52dd0c01-e803-423a-be5f-b592b5d61c"。

リクエスト例：

ユーザー入力待ちのSIPSをリストアップ¶

GET

/api/ingest/waiting

ユーザー入力を待っているSIPのリストを返します。

レスポンスの定義：

message

"ユニットの取得に成功。"

results:

キーを持つ辞書のリスト：

sip_directory ：SIPが現在あるディレクトリ。

sip_uuid ：SIPのUUID。

sip_name ：SIPの名前。

microservice ：現在のマイクロサービスの名前。

注釈

URLとは裏腹に、これは現在、ユーザー入力待ちのSIPと転送（forward）の両方を返します。将来的には、転送（transfer）に /api/transfer/ waiting が追加されるはずです。

リクエスト例：

curl -X GET \
  http://mytestinstance.archivematica.net/api/ingest/waiting \
  -H 'Authorization: ApiKey admin:ooha0sshie8O' \
  -H 'Host: mytestinstsance.archivematica.net' \

メタデータをコピー¶

POST

/api/ingest/copy_metadata_files/

SIPにメタデータファイルを追加します。

リクエストボディのパラメーター：

sip_uuid

ファイルを配置するSIPのUUID。

source_paths[]

コピーされるファイルのリスト。base64エンコードされ、フォーマットは、「source_location_uuid：full_path」です

レスポンスの定義：

error

ブール値のtrueまたはfalse。

message

Success message or reason for the error.

Usage example:

curl -X POST \
    http://my_archivematica_instance.archivematica.org/api/ingest/copy_metadata_files/ \
    -H 'Authorization: ApiKey [_your_username_]:[_your_ApiKey_]' \
    -H 'Content-Type: application/x-www-form-urlencoded' \
    -d 'sip_uuid=a7f1f36c-55c1-4fb7-a898-76d102e847dc&source_paths%5B%5D= \
    'NmRjYTgxNDAtMDg2NC00MzE5LTg2ZDctNTg0ZjZiZTY4N2EzOi9ob21lL2FyY2hpdmVtYXRpY2EvYXJjaGl2ZW1hdGljYS1zYW1wbGVkYXRhL2lzc3VlX3RlbXBsYXRlLm1k''

レスポンス例

201 Created:

{
  "error": false,
  "message": "Metadata files added successfully."
}

400 Bad Request:

{
  "error": true,
  "message": "sip_uuid and source_paths[] both required."
}

500 Internal Server Error:

{
  "error": true,
  "message": "Location 6dca8140-0864-4319-86d7-584f6be687a3 is not associated with this pipeline"
}

ユニット¶

ユニットとは"、アクセス補助が使用するアーカイブ情報ユニットに関する情報を提供するために特化されたパッケージ記述の一種を指します。"（OAIS、p.1-13、セクション1.7.2）

ジョブ一覧¶

GET

/api/v2beta/jobs/<unit UUID>/

渡されたユニット（転送またはインジェスト）のジョブのリストを返します。

クエリ文字列パラメーター（オプション）：

microservice

ジョブが属するマイクロサービスの名前。

link_uuid

ジョブチェーンリンクのUUID。

name

ジョブ名。

detailed

If the parameter is included in the request, the endpoint returns all the task properties provided by the タスク endpoint.

応答定義（ディクションのリストから）：

uuid

ジョブのUUID。

name

ジョブ名。

status

USER_INPUT、PROCESSING、COMPLETE、FAILED、UNKNOWN のいずれか1つ。

microservice

ジョブが属するマイクロサービス。

link_uuid

ジョブチェーンリンクのUUID。

tasks

マイクロサービスのタスクに関する情報を持つ辞書のリスト。

uuid

タスクのUUID。

exit_code

タスクの終了コード。

リクエスト例：

  curl -X GET \
  'http://mytestinstance.archivematica.net/api/v2beta/jobs/a06ac9b9-0d67-420a-befb-80ea9a562190/?name=Store%20the%20AIP&microservice=Store%20AIP&link uuid=a06ac9b9-0d67-420a-befb-80ea9a562190&link%20uuid=a06ac9b9-0d67-420a-befb-80ea9a562190' \
  -H 'Accept: */*' \
  -H 'Connection: keep-alive' \
  -H 'Host: mytestinstance.archivematica.net' \
  -H 'User-Agent: PostmanRuntime/7.15.0' \
  -H 'accept-encoding: gzip, deflate' \
  -H 'authorization: ApiKey analyst:oohah5chashie8OwEih6udie4choo3la' \
  -H 'cookie: csrftoken=sb52U8S35EpdB2T1K4lWXFl5jNnOrXrA' \
  -b csrftoken=sb52U8S35EpdB2T1K4lWXFl5jNnOrXrA

レスポンスの例（JSONボディ）：

ベータ¶

まだ流動的で、変更の可能性があるAPIエンドポイント。

パッケージ¶

POST

/api/v2beta/package

新しい転送タイプを開始します。

リクエストボディパラメーター（必須）：

name

転送名。

path

Storage Service転送元に対する相対パス、または絶対パス。

リクエストボディパラメーター（オプション）：

type

転送タイプ。有効な値は、standard、zipfile、unzip bag、zip bag、dspace、maildir、TRIM、dataverseです。デフォルト：standard。

processing_config

処理設定（例：デフォルト、自動化、デフォルト：デフォルト）

accession

Accession ID。

access_system_id

アクセスシステムID（ Docs を参照）。

metadata_set_id

ユーザーインターフェース経由で追加されたメタデータセットへのリンクに使用されます。メタデータは、今のところ API経由で転送に関連付けることができないので、当面これは無視しても大丈夫です。

auto_approve

ブール値trueまたはfalseで、転送を自動承認に設定します。

レスポンスの定義：

id

転送UUID（注意：パッケージエンドポイントは、呼び出し元がArchivematicaと非同期でやり取りできるようにするものであり、転送が開始されたことを保証するものではありません。呼び出し側はレスポンスのUUIDを使用して、転送が開始されたこと、または転送を開始する際にエラーが発生したことを確認する必要があります）

例：

ほとんどのユースケースでは、これらのオプションのサブセットのみが必要になる場合があります。パッケージエンドポイントと、転送を開始できる他のエンドポイントとの基本的な違いは、Storage Serviceの転送場所 UUID が必ずしも必要ではないことです。場合によっては、それが依然として理想的な場合もあります。

絶対パスを用いた転送の開始

curl \
    --request POST \
    --header "Authorization: ApiKey test:test" \
    --header "Content-Type: application/json" \
    --data "{\
       \"path\": \"$(echo -n '/home/archivematica/archivematica-sampledata
       /SampleTransfers/DemoTransfer' | base64 -w 0)\", \
       \"name\": \"demo_transfer_absolute\", \
       \"processing_config\": \"automated\", \
       \"type\": \"standard\" \
      }" \
        "http://<archivematica-uri>/api/v2beta/package"

転送元 UUID による相対パスを用いた転送の開始

curl \
    --request POST \
    --header "Authorization: ApiKey test:test" \
    --header "Content-Type: application/json" \
    --data "{\
       \"path\": \"$(echo -n 'd1184f7f-d755-4c8d-831a-a3793b88f760:
       /archivematica/archivematica-sampledata/SampleTransfers/DemoTransfer'
       | base64 -w 0)\", \
       \"name\": \"demo_transfer_relative\", \
       \"processing_config\": \"automated\", \
       \"type\": \"standard\" \
      }" \
        "http://<archivematica-uri>/api/v2beta/package"

妥当性確認¶

/api/v2beta/validate/<validator>

Archivematica 1.10+で利用可能です。このエンドポイントを使用して、埋め込まれたルールセットに対してCSVを妥当性確認できます。現在、Avalon Media System Manifest（ ``avalon`` ）およびrights.csv（ ``rights`` ）ファイルで動作します。

将来的には、このエンドポイントを拡張して、metadata.csvやarchivesspaceids.csv、あるいはその他の機関ベースのルールに対する妥当性確認をサポートできます。

レスポンスの定義：

valid

ブール値のtrueまたはfalse。

reason

妥当性確認エラーを含みます。

使用例（avalon.csv が存在する場合）:

curl \
  --data-binary "@avalon.csv" \
  --header "Authorization: ApiKey test:test" \
  --header "Content-Type: text/csv; charset=utf-8" \
    http://127.0.0.1:62080/api/v2beta/validate/avalon

レスポンス例

200 OK:

{
  "valid": true
}

400 Bad Request（異なる妥当性確認エラーが含まれることを想定）:

{
  "valid": false,
  "reason": "Administrative data must include reference name and author."
}

404見つかりません:

{
  "error": true,
  "message": "Unknown validator. Accepted values: avalon"
}
